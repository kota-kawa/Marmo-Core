# 重构路线图生成器

## 目标

把扫描发现的问题，按照「收益/风险」比排序，生成一份可以按周执行的重构计划。

> 重构最大的陷阱是"一次改太多"。这个计划的原则是：
> 每一步都可以独立提交、独立测试、不影响其他功能。

---

## 第零步：读取前置文档

同时用 Read 工具读取：
1. `codebase-scan-report.md` — 获取问题清单
2. `COMPONENT-STANDARDS.md` — 获取目标规范

两个文件都必须存在，否则依次提示用户先运行 `/codebase-scan` 和 `/standards-gen`。

---

## 第一步：问题分类与评分

对扫描报告中的每个问题，按两个维度评分（1-3分）：

**改动收益**（改了之后有多大价值）：
- 3分：阻塞其他重构、或影响多个功能的核心问题
- 2分：独立的质量问题，改了之后有明显提升
- 1分：锦上添花，不改影响不大

**改动风险**（改动有多可能引发 bug）：
- 3分：高风险（核心业务逻辑、无测试覆盖、多处引用）
- 2分：中风险（有一定引用、逻辑较复杂）
- 1分：低风险（独立组件、纯 UI、有测试）

**优先级得分 = 收益 × (4 - 风险)**（高收益低风险的优先）

---

## 第二步：生成三个阶段

### Phase 1：基础设施（第 1-2 周）
**原则**：不动业务逻辑，只建规范框架

包含：
- 建立 `src/composables/` 目录，提取最通用的 composable（如 `useAsync`、`useStorage`）
- 建立 `src/api/` 目录，把最常见的 API 调用封装起来
- 确定 `atoms/` 目录，将已有的纯 UI 组件移入（只移动，不改逻辑）
- 在项目根目录放置 `COMPONENT-STANDARDS.md`，让团队知道规范

> 这一步改完，后续所有重构都有"落脚点"，不会再出现"提取出来放哪里"的困惑。

---

### Phase 2：高收益低风险重构（第 3-6 周）
**原则**：用 Phase 1 建好的基础，开始消灭最明显的问题

从扫描报告的「超大组件」列表中，筛选出：
- **低风险**（优先级得分最高）的组件，逐个处理
- 每个组件用 `component-atomizer` Agent 分析后再动手

每个组件的处理步骤：
1. 运行 `component-atomizer` 获取拆分方案
2. 先提取 composable（不动 template）
3. 再拆子组件（不动业务逻辑）
4. 提交，测试，再处理下一个

---

### Phase 3：系统性规范化（第 7 周以后）
**原则**：收尾，消灭剩余的不规范项

包含：
- 处理 Phase 2 未覆盖的中等组件
- 统一目录结构到规范形态
- 清理禁止项清单中的违规代码
- 更新路由配置（如果目录结构有变化）

---

## 第三步：生成任务清单

用 Write 工具写入 `REFACTOR-PLAN.md`：

```markdown
# 重构路线图

> 生成时间：[日期]
> 基于：codebase-scan-report.md + COMPONENT-STANDARDS.md

## Phase 1：基础设施（第1-2周）

### 任务清单
- [ ] 创建 src/composables/useAsync.ts
- [ ] 创建 src/composables/useStorage.ts
- [ ] 创建 src/api/ 目录，迁移 [扫描报告中直接调 API 最多的 N 个组件] 的请求逻辑
- [ ] 整理 atoms/ 目录，迁移 [列出具体文件]
- [ ] 提交 COMPONENT-STANDARDS.md 到仓库

## Phase 2：高收益重构（第3-6周）

按顺序处理以下组件（每个独立提交）：
1. [组件名] — [原因：script N行，重复逻辑X处]
2. [组件名] — ...

## Phase 3：系统规范化（第7周+）

### 剩余组件
[列出 Phase 2 未处理的组件]

### 禁止项清理
[列出扫描到的禁止项违规，逐条处理]
```

---

## 重要提醒（输出到报告末尾）

```
⚠️  重构纪律

1. 每次只动一个组件，动完提交，不要积累未提交的改动
2. 重构 = 不改行为。如果顺手修了 bug，单独提交，不要和重构混在一起
3. 遇到不确定的地方，先用 component-atomizer 分析，再动手
4. Phase 1 没做完之前，不要开始 Phase 2
```
