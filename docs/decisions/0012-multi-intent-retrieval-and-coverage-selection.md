# 0012. 複数意図のゴールは分解して検索し、集合はファセット被覆で選ぶ（opt-in）

- 状態: Accepted
- 日付: 2026-11-24
- 根拠: `marmo_core/decomposition.py`、`marmo_core/coverage.py`、
  `benchmarks/run_toolret_benchmark.py`、`benchmarks/results/toolret.json`、
  `benchmarks/README.md` の「ToolRet」節

## 文脈

既存の評価はリポジトリ内で作ったコーパスとラベルで、ゴールの大半は 1 つの要求だった。
公開ベンチマーク ToolRet（ACL 2025 Findings、35 データセット、44,453 ツール）では
1,689 クエリの標本のうち 726 件が複数ツールを正解に持ち、次の 2 つが測定で分かった。

1. 1 回の検索はゴール全体の文に対して候補を順位づけるため、支配的な要求のツールが上位を
   占め、他の要求のツールが落ちる。字句検索で複数ツールのクエリの全正解が上位 10 件に入るのは
   6.5% だった。
2. 既存のソルバーは Σu（選んだ単位のスコア合計）を最大化するため、関連していそうな候補を
   足すほど目的関数が増え、集合の大きさを決められない。固定 top-3 の Set F1 は 0.12 だった。

## 判断

`Kernel` の既定値は変えず、拡張点として次を追加する。

- `DecomposedRetriever`: `QueryDecomposer` でゴールを下位タスクに分け、内側の Retriever で
  ゴールと各下位タスクを検索して融合する。既定の `fusion="blend"` は
  `(ゴール関連度 + 0.25 × 最良の下位タスク関連度) / 1.25` を合成スコアの関連度成分に差し替え、
  各結果に下位タスクごとの関連度（`facet.<i>` 成分）を付ける。重み 0.25 は ToolRet の dev 分割で
  選んだ。ゴール側は、ゴールの語のうちカタログの索引に存在する語の割合（既知語率）で重み付けする
  （`discount_unknown_terms=True`）。関連度はカタログが知っている語だけで測るため、カタログと
  別の言語で書かれたゴールは、わずかな既知語（人名・数値）だけで高い関連度になる。未知の語を
  「一致しなかった語」として数えることで、英語で書かれた下位タスクに順位を委ねる。
- `LLMQueryDecomposer`: 1 回の LLM 呼び出しで下位タスクと暗黙の前提手順を JSON 配列で返させる。
  失敗時は分解なし（ゴールのみの検索）に縮退し、既存の LLM 支援層と同じ方法で警告と
  `failures` / `last_failure` に残す。
- `CoverageSetSelector`: ファセット被覆の facility-location 目的
  `F(S) = Σ_k Σ_f w_f · max_{i∈S, kind(i)=k} r_f(i)` を貪欲に最大化し、限界利得が `min_gain`
  （既定 0.1）を下回ったら止める。被覆は種別 k ごとに数える。Memory・Skill・Tool・Agent は
  役割が違い、同じ下位タスクに効く Tool があっても Skill や Memory は冗長にならないため。
  単位（依存閉包）、競合、権限、件数・種別・予算の制約と abstain / escalate の扱いは
  `GreedyConstrainedSetSelector` と同じヘルパーを使う。F は単調劣モジュラなので、基数制約下の
  貪欲法は (1 − 1/e) 近似になる。
- `ClauseQueryDecomposer`: 依存なしの規則ベース分解。比較用の基準線として残すが、推奨しない。

## 影響

- ToolRet の test 分割（856 クエリ、MiniLM-L6 埋め込み + BM25F の hybrid、LLM 分解は Claude
  Sonnet）で、分解と blend 融合は nDCG@10 を +0.019（95% CI [0.012, 0.026]）、Completeness@10 を
  +0.012 [0.001, 0.023] 改善した。数値は `benchmarks/README.md` と
  `benchmarks/results/toolret.json`。
- 集合選択の改善の大半は順位付けから来た。分解前の top-1 から分解後の被覆型までの Set F1
  +0.022 のうち +0.017 は分解後の top-1 で得られ、被覆型の上積みは +0.004 [−0.005, 0.014] で
  有意ではない。被覆型は集合が小さく Exact が高いが、首位比 0.9 の相対しきい値が F1 で上回った
  （0.189 対 0.181）。ToolRet の正解には近い候補（同じ API の複数エンドポイント）が並ぶため。
  被覆型を残すのは、下位タスクと種別ごとに 1 つずつ選び、依存閉包・競合・権限・予算の制約と
  abstain / escalate を保つ集合選択だからで、F1 の最大化が目的なら相対しきい値か LLM を使う。
- `LLMSetSelector`（Sonnet、上位 20 件）は F1 0.243（top-1 比 +0.067 [0.049, 0.086]）で最良だった。
  リポジトリ内の宣言制約付き合成ベンチマークではソルバーが LLM に勝ったが（ADR 0005）、ToolRet には
  宣言制約がなく、記述の意味を読む判断が効く。Kernel はどの Selector の出力にも制約をかけるので、
  関連性を LLM に、制約をソルバーに任せる構成は ADR 0005 と矛盾しない。
- 日本語に訳したゴール（206 件）では、字句検索と英語専用の埋め込みはほぼ機能せず
  （nDCG@10 0.013 / 0.029）、割引なしの分解は 0.057、割引ありは 0.134 だった。同じクエリの英語版
  では割引の有無で差がなかった（0.268）。重みを固定で上げる案（1.0）は日本語で同等だったが、
  英語の dev で分解の利得がほぼ消えた（nDCG@10 0.276 → 0.266）ため、固定値ではなく既知語率で
  切り替える。
- 規則ベース分解は利得がなかった。単一ツールのクエリの 60%（LLM は 34%）を誤って分解し、
  BM25 上ではどの融合重みでも dev の nDCG@10 が下がり、hybrid 上でも有意差がなかった
  （test +0.005 [−0.000, 0.010]、dev −0.008）。分解の利得は分解の精度に依存する。
- 1 ゴールあたりの検索は `1 + 下位タスク数` 回になり、LLM 分解は 1 回のモデル呼び出しを足す。
  予算付きタスクでは `budget_aware` を宣言していないため Kernel が拒否する。
- `facet.<i>` 成分は `DecomposedRetriever` と `CoverageSetSelector` の間の取り決めである。
  成分が無い結果では被覆型はゴール 1 ファセット（`relevance`）として振る舞い、種別ごとに最良の
  単位を選ぶ。4 種混合の集合選択ベンチマーク（28 シナリオ、lexical、pool 63）では、種別を区別
  しない被覆が Set F1 0.536 / Exact 0% だったのに対し、種別ごとの被覆は greedy と同じ
  0.609 / 54%（閉包 100%、abstain/escalate 100%）になった。
- 第1層の精度が全体の上限を決める状況は変わらない。ToolRet の首位の Set F1 は 0.18 前後で、
  集合選択の改善幅もそれに縛られる。LLM 再ランクを重ねると nDCG@10 は +0.043 になった。

## 代替案

- RRF 融合: ゴールのリストを重み付けしても、dev で blend を下回った。オプションとして残す。
- 下位タスクの重みを固定で 1.0 にする: 上記のとおり英語での利得を失う。
- 最良スコアの max 融合: 短い下位タスクほど関連度が高く出るため、単一ツールのクエリで大きく
  劣化した。採らない。
- 首位関連度に対する相対しきい値で集合サイズを決める: 分解後の順位では F1 で被覆型を上回った
  （0.189 対 0.181）。独立した Selector にはせず、被覆型の `include_within`（被覆の後に、首位候補の
  関連度の一定割合以上の候補も制約内で残す）として入れた。dev で選んだ 0.95 で test 0.189。既定は
  `None`（近い候補を落とす精度寄りの挙動）のまま。
- 候補ごとの所属確率をロジスティック回帰で較正し、期待 F1 を最大化する k を選ぶ: 字句検索では
  確率がどれも低く top-1 と変わらなかった。
- 入出力名の一致による前提ツールの補完（データフロー補完）: 正解集合の 28% に入出力名の連鎖が
  あったが、起点の首位が誤っていることが多く、改善は F1 +0.01 未満だった。
