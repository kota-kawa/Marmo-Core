# 0015. タスクの実行権と呼び出しジャーナル

[English](0015-execution-right-and-call-journal.en.md)

- 状態: Accepted
- 日付: 2026-11-27
- 根拠: `marmo_core/state.py`、`marmo_core/kernel.py`、`marmo_core/budget.py`、`tests/test_kernel_execution_integrity.py`、`tests/test_state_concurrency.py`

## 文脈

同じ State Store を使う二つの Kernel が同じタスクのハンドラーに両方到達できた。状態の競合が
分かるのはハンドラー実行後だった。結果の `step` event を保存した直後にプロセスが止まると、
続きの位置（`frame` / `plan`）が古いまま残り、再開時に同じハンドラーがもう一度呼ばれた。
モデル応答を待つ間の `cancel()` は、遅れて届いた結果の `completed` で上書きされた。
予算の予約は残高確認と追記が別々で、別接続から上限を超えて予約できた。

## 判断

- **実行権**: `Kernel.run` / `resume` は `StateStore.execution(task_id)` を取ってから動く。
  取れなければ副作用の前に `StateConflictError` で止まる。JSONL と SQLite のストアは OS の
  ファイルロックで他のインスタンス・プロセスも排他し、保持者が落ちればロックは解放される。
  基底クラスの既定は同一インスタンス内だけを排他する。
- **呼び出しジャーナル**: 呼び出し ID ごとに、ランタイムへ渡す前の `call` event（`started`）、
  結果の `step` event（`call_id` 付き）、続きの位置を保存した event の `closed_calls` を記録する。
  再開時、閉じていない記録に結果があればハンドラーを呼ばずその結果から続ける。着手だけなら
  結果不明（`timeout`）として記録し、ADR 0008 と同じく自動では再試行しない。
- **終端状態**: 状態を変える書き込み（`status` / `paused` / `resumed`）は、判断した時点の版を
  条件にした追記で行い、すでに終端なら書かない。キャンセル後は新しい呼び出しを始めない。
- **予算**: 予約と精算は、残高を読んだ版を条件にした追記にし、競合したら読み直す。
- 状態ファイルは `schema_version: 1` のまま。`call` は追加の event kind で、`step` の
  `call_id` と `closed_calls` は追加のキーである。これらを持たない旧形式のログは従来どおり読める。

## 影響

- モデルループは、モデルが Tool を要求した直後に `frame` を保存する。1 ラウンドにつき
  event が 1 件、呼び出し 1 回につき `call` event が 1〜2 件増える。
- 実行中のタスクに対する二つ目の `run` / `resume` は例外になる。これまでは両方が進んだ。
- 独自の `StateStore` サブクラスは、他プロセスとの排他が必要なら `_execution_guard` を実装する。
- ハンドラーが完了してから結果を保存するまでの間に止まった呼び出しは、結果不明として人に
  確認を求める。実際には成功していても自動では進まない。

## 代替案

- 状態の版だけで競合を検出する方式は、検出がハンドラー実行後になるため採らない。
- 期限付きのリース（行やファイルに持ち主と期限を書く）は、落ちた保持者の解放に時計と
  更新処理が要る。OS のロックは保持者の終了で解放されるため、こちらを採った。
- 結果と続きの位置を 1 件の event にまとめる方式は、再試行・代替・並行ステップの経路を
  大きく組み替える必要があるため見送った。
