# 0013. 選択の状態は LLM に決めさせず、要求ごとの能力判定と宣言制約から決める（研究用 opt-in）

- 状態: Proposed（研究用 opt-in。事前登録した採用基準の 1 つを、2 回の評価とも満たさなかったため、推奨・既定化はしない）
- 日付: 2026-11-26
- 根拠: `marmo_core/requirement_coverage.py`、`benchmarks/run_toolret_sae.py`、
  `benchmarks/results/toolret-sae.json`、`benchmarks/README.md` の「ToolRet-SAE」節

## 文脈

#35 の主張は「ツール選択は順位付けではなく、権限・依存制約つきの集合選択と、棄権（abstain）・
人に上げる（escalate）判断である」。公開ベンチマークの ToolRet にはどのクエリにも答えがあり、
どのツールも使えるので、棄権とエスカレートを測れなかった。そこで ToolRet の 1,689 クエリから
S（正解の権限あり）、E（正解のスコープだけ未付与）、A（正解をカタログから削除）の 3 変種を作り、
評価対象と別のモデル（Claude Opus）が、全手法の見る上位 20 候補に代替ツールがあるかを判定して
正解の状態を確定した（ToolRet-SAE）。

この上で、既存の 2 方式はどちらも状態を決められなかった。

1. 関連度の下限（規則ベース）: dev で最適化すると「ほぼ常に棄権する」退化解になり、
   マクロ正答率 0.344 は「常に棄権」の 0.333 とほぼ同じだった。下限なしでは A（正解なし）で
   一度も棄権しない。答えられる依頼と答えられない依頼の関連度の分布が重なっているため。
2. `LLMSetSelector`（集合と状態を 1 回の LLM 呼び出しで返させる）: 0.298 で、調整済みの
   下限（0.344）にも劣った。A で 76% が何かを選び、E で 68% が許可された別のツールを選んだ。
   正解を候補に入れた条件でも、E の 50% で権限の無い正解の代わりに別のツールを選んだ。

## 判断

`RequirementCoverageSelector` を研究用 opt-in として追加する。

- LLM の役割を「タスクの要求を列挙し、要求ごとに満たす候補を挙げる」だけに限る。プロンプトには
  名前・種別・説明だけを渡し、権限・費用・信頼度・制約規則は渡さない。
- 状態はソルバーが決める。満たす候補が無い要求があれば abstain（権限を与えても解決しない）、
  権限で阻まれた候補しか満たさない要求があれば escalate（不足が最小の権限を返す）、
  そうでなければ依存閉包単位の貪欲集合被覆で selected とする。
- `per_requirement="all"` は被覆の後に、判定で挙がった他の実行可能な候補も残す。
  dev で事前登録どおりに選んだ（S の Set F1 0.336 対 0.323）。

ADR 0005（制約は LLM ではなくソルバーが解く）を状態の決定にまで広げたものになる。
`Kernel` と既存 Selector の既定は変えない。`marmo_core` からは再エクスポートしない。

## 影響

ToolRet-SAE の test 分割（856 クエリ、有効な変種 S 856・E 546・A 472、検索は
`llm:hybrid-0.5`、LLM は Claude Sonnet）での主指標（S / E / A の正答率のマクロ平均。
S は必要な正解ツールまたは代替を全部含む集合を選んだときだけ正答）:

- `per_requirement="all"`: 0.447。dev で調整した最良の規則（greedy、下限 0.75）比 +0.103
  [0.077, 0.129]、`LLMSetSelector` 比 +0.149 [0.130, 0.169]。
- 正解を候補に入れた条件（test 445 クエリ）では、E+ で escalate できた割合が 0.796
  （`LLMSetSelector` 0.475）、無関係なツールを選んだ割合が 0.165（同 0.502）。
  正解ありの S+ で十分な集合を選べた割合は 0.838 で、`LLMSetSelector`（0.928）より低い。
- 1 回の選択あたりの LLM 呼び出しは 1 回で、`LLMSetSelector` と同じ。権限が違うだけの
  同じ候補には判定を再利用する。

結果を見る前に決めた採用基準は 4 つで、そのうち 3 つ目を満たさなかった。
S（正解あり）での不要な escalate が 0.060 で、`LLMSetSelector`（0.023）+ 0.02 を超えた。
誤りを分析すると、51 件中 42 件は候補 20 件の中に「許可された正解・代替」が無く、
権限の無い類似ツールしか残っていない状況だった。主な原因は検索の取りこぼしだが、
基準は事後に変えない。このため推奨とはしない。

残る誤りの大半は能力判定の甘さである。A で何かを選んだ 194 件のうち、ラベル上の代替を
含むのは 40 件だけだった。判定の厳しさを上げる工夫と、検索の上限（上位 20 件に正解が揃うのは
32%）の改善が、次の改善余地になる。

限界: 正解の状態は LLM アノテータによる。第 2 アノテータ（Sonnet）との一致度は
代替判定で κ=0.80、変種の有効性で κ=0.78 だったが、人によるラベルではない。手法の判定も
Sonnet なので、同系統のモデルどうしの相関が結果を有利にしている可能性は排除できない。
権限は不透明なスコープ（ハッシュで割り当て）で、実際の権限体系の意味は持たない。

**採用基準（4 つとも満たせば opt-in として `main` に提案する。1 つでも満たさなければ推奨しない）**

1. dev で主指標が最良の規則（`GreedyConstrainedSetSelector`、下限 0.55）を上回り、差の CI が 0 を含まない。
2. `LLMSetSelector` に劣らない（差の CI 下限 > −0.02）。
3. S での不要な escalate が `LLMSetSelector` + 0.02 以下。
4. 1 回の選択あたりの LLM 呼び出しが最大 2 回（#45 で前回の「1 回」から改めた。平均も報告する）。

**逸脱の記録**: 事前登録の前に、指定の誤りで held-out の約 360 件に Sonnet のラベルが付いた。分解前の候補に対する

**限界**: ラベルは LLM（Sonnet）による。人による検証は行わない（#48 で範囲を縮小した）。手法とラベルが同系統の
モデルなので、相関が結果を有利にしている可能性は排除できない。held-out は 60 件を超えるサブセット（18 個）からしか
取れず、前回の test とは構成が違う。

## 追記: held-out での結果（2026-11-27）

事前登録した設定（`judge="strict"`、追加検索なし、`per_requirement="best"`）を held-out の 400 件で一度だけ評価した
（`benchmarks/results/toolret-sae-heldout.json`、有効な変種 S 400・E 205・A 167）。

| 基準 | 結果 |
|---|---|
| 1. 最良の規則（greedy、下限 0.55）を上回り、CI が 0 を含まない | 満たす。+0.165 [0.123, 0.211]（0.552 対 0.386） |
| 2. `LLMSetSelector` に劣らない | 満たす。+0.176 [0.143, 0.211]（`LLMSetSelector` は 0.376） |
| 3. S の不要な escalate が `LLMSetSelector` + 0.02 以下 | **満たさない**。0.070、上限は 0.020 + 0.02 = 0.040 |
| 4. LLM 呼び出しが最大 2 回 | 満たす。1 回 |

基準 3 が再び未達なので、状態は Proposed のままとし、`main` への提案はしない。

- 主指標の優位は、モデル（Sonnet → Haiku）、アノテータ（Opus → Sonnet）、分割を替えても再現した。
- 不要な escalate は厳格な判定でも下がらなかった。28 件中 18 件は候補 20 件に許可された正解・代替が無い状況で、
  同じ候補を見る greedy も 0.068 だった。`LLMSetSelector` の 0.020 は、E の 58% で権限の無い正解の代わりに別の候補を
  選ぶ性質と表裏であり、「escalate すべきときに escalate する」手法がこの基準を満たすには、検索の取りこぼしを減らすか、
  次点の候補を誤って選ばない判定が要る。追加検索の経路は dev で不要な escalate を 0.055 から 0.035 に下げたが、E の
  誤選択を増やして主指標を下げた。
- 基準 3 の上限が比較相手の誤りに引きずられる形になっている点は、次に評価するなら見直す候補である（事後には変えない）。
- 第 2 アノテータ（Haiku、100 件）との一致度は、代替判定 κ=0.80、必要性 κ=0.79、変種の有効性 κ=0.88。人による検証と
  別系統のモデルによる検証は行っていない（#48）。

## 代替案

- 関連度の下限で棄権を決める: 上のとおり退化解になる。
- `LLMSetSelector` に状態まで決めさせる: 上のとおり E と A で選んでしまう。
- LLM に権限も見せて要求判定させる: ADR 0005 の観測（権限名から宣言されていない権限要求を
  推論した）と同じ失敗を招くので試していない。
- 要求を `TaskSpec` の型付き要求として抽出し、資源契約と照合する（`GoalAwareSetSelector`）:
  ToolRet の資源には契約が無く、自然言語の説明しか無いため比較できない。
