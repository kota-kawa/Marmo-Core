# 0005. 集合選択の制約はソルバーで解き、LLM や検索時フィルタに委ねない

- 状態: Accepted
- 日付: 2026-07-17
- 根拠: `benchmarks/README.md`（集合選択、Policy アブレーション、B&B 比較）、`selector.py`

## 文脈

依存閉包、競合、権限、予算の制約を満たす集合を選ぶ第2層について、Top-K、貪欲、ビーム、
分枝限定法、LLM（gpt-4o / gpt-4o-mini）を同条件で比較した。また権限制約を課す位置を
検索時フィルタ／選択器内／後段ゲートの 5 条件で比較した。

## 判断

- 制約は宣言メタデータに対してソルバー（既定は `GreedyConstrainedSetSelector` の閉包単位
  効用順）で解く。LLM Set Selector は比較対象として残すが既定にしない。
- 権限制約は選択器内で解く。検索時のハードフィルタ（pushdown）は行わない。後段ゲートは
  バイパス防止の多層防御として残す。

## 影響

- LLM は最良条件でも Set F1 0.628 / Exact 25% で greedy（0.720 / 62%）に届かず、
  過少選択が主因。レイテンシは 4 桁大きい。
- 検索時フィルタは「権限があれば実行可能」なケースを abstain に劣化させ、abstain/escalate
  精度が 100% → 50% に落ちる。HITL への接続が失われる。
- 厳密解（B&B）でも greedy を超えない。ボトルネックは探索ではなく効用関数であり、改善は
  `u(i,q)` への構造情報の反映（capability グラフ、実績メタデータ）に向ける。

## 代替案

- LLM に集合を選ばせる: 上記の通り却下。制約の推論を自然言語に委ねると、宣言されていない
  権限要求を推論して全滅する挙動も観測された。
- 検索時に権限で絞る: 安全だが escalate 能力を壊すため却下。
