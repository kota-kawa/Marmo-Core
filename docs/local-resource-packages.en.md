# Local Resource Packages

[日本語](local-resource-packages.md)

Local resource packages in Marmo-Core provide a common format for sharing Memory,
Skill, Tool, and Agent resources, and check compatibility and integrity before
loading them. They require no additional dependencies.

A complete example is available in [`examples/package-template`](../examples/package-template).

## Directory structure

```text
my-package/
  marmo-package.json       # package manifest (edited by hand)
  marmo-package.lock.json  # pinned SHA-256 hashes and source (generated by the CLI)
  resources.json           # one or more resource definitions
  skills/
    review/SKILL.md        # available when listed in the manifest
```

Files not listed in the manifest are not loaded as part of the package. Absolute
paths, `..`, and symlinks that point outside the package are rejected.

## Manifest

The filename must be `marmo-package.json`.

```json
{
  "schema_version": 1,
  "namespace": "com.example",
  "name": "operations",
  "version": "1.2.0",
  "description": "Operations resources",
  "kernel": ">=0.3.0,<1.0.0",
  "resources": ["resources.json", "skills/review/SKILL.md"],
  "dependencies": [
    {"name": "com.example/foundation", "version": "^1.0.0"}
  ]
}
```

The fields mean the following:

| Field | Required | Description |
|---|---:|---|
| `schema_version` | Yes | Currently `1` |
| `namespace` | Yes | An owning namespace made of lowercase letters, digits, `-`, and `.` |
| `name` | Yes | The package name within the namespace |
| `version` | Yes | The package's SemVer version |
| `description` | No | A description of the package |
| `kernel` | Yes | The supported Marmo-Core version range |
| `resources` | Yes | File paths relative to the package root |
| `dependencies` | No | Local packages to load together and their version ranges. When omitted, the package has no dependencies (an empty array) |

The required fields are `schema_version`, `namespace`, `name`, `version`, `kernel`, and `resources`. `resources` needs at least one entry, and each file must end in `.json` or `.md`. Only `description` and `dependencies` may be omitted.

Version ranges support exact matches, `>`, `>=`, `<`, `<=`, comma-separated
AND conditions, caret (`^1.2.3`), tilde (`~1.2.3`), and `*`. OR with `||` is
not supported.

Packages are identified as `namespace/name@version` (for example,
`com.example/operations@1.2.0`). Loading a parent directory also makes Marmo-Core
discover packages beneath it and check that dependencies exist and satisfy
their SemVer ranges.

## Resource definitions

JSON can still use a single resource, an array of resources, or
`{"resources": [...]}`. One entry represents the common metadata, implementation,
dependency declarations, and kind-specific metadata.

```json
{
  "id": "tool.com.example.read-report",
  "kind": "tool",
  "name": "Read report",
  "version": "1.0.0",
  "description": "Read one report.",
  "capabilities": ["report reading"],
  "input_summary": "A report path",
  "output_summary": "Report text",
  "required_permissions": ["fs.read"],
  "cost_estimate": 0.0,
  "latency_class": "fast",
  "side_effect": "read",
  "trust_level": "verified",
  "ref": "tool://com.example/read-report",
  "tags": ["report"],
  "dependencies": ["memory.com.example.report-policy@1.0.0"],
  "input_schema": {
    "type": "object",
    "required": ["path"],
    "properties": {"path": {"type": "string"}}
  },
  "output_schema": {"type": "object"},
  "isolation_level": "L2"
}
```

Resource IDs must use the form `<kind>.<namespace>.<local-name>`, including the
kind and the manifest namespace. For example, when the namespace is
`com.example`, Tools use `tool.com.example.*` and Agents use
`agent.com.example.*`. This check prevents accidentally overwriting another
package's namespace.

The main implementation fields for each kind are:

- Memory: `content`
- Skill: `instructions` (or the body of `SKILL.md`)
- Tool: `input_schema`, `output_schema`, `isolation_level`
- Agent: `delegation_interface`, `model`, `system_prompt`

When `SKILL.md` is listed in the manifest, its resource ID is generated
automatically under the package namespace. For namespace `com.example` and
`skills/review/SKILL.md`, the ID is `skill.com.example.review` (the leading
`resources/` and `skills/` components are removed from the directory path
relative to the package root, and the remaining components are joined with
`__`). To keep an ID fixed, specify `id` in the front matter. An explicit `id`
always takes precedence.

```markdown
---
id: skill.com.example.review
name: review
version: 1.0.0
description: Review a report.
dependencies: [memory.com.example.report-policy@1.0.0]
---
```

## Locking and verification

After reviewing the manifest and resources, create the lock file.

```bash
marmo package lock ./my-package
marmo package verify ./my-package
marmo package inspect ./my-package
marmo validate ./my-package
```

`marmo-package.lock.json` records:

- The package's full identity
- The source type `local` and a relocatable source path (default: `.`)
- The manifest's SHA-256 hash
- The SHA-256 hash of each resource listed in the manifest

If you intentionally change the manifest or a resource, review the diff and
then run `marmo package lock` again.

`marmo package verify` and `marmo validate` guarantee different things.

| Check | `marmo package verify` | `marmo validate` |
|---|:---:|:---:|
| Manifest schema (required fields, namespace, SemVer, resource paths) | Yes | Yes |
| Compatibility with the kernel version range | Yes | Yes |
| The lock exists, matches the package identity, and lists exactly the manifest's files | Yes | Yes |
| SHA-256 of the manifest and every listed resource file matches the lock | Yes | Yes |
| Every package in `dependencies` is loaded together and satisfies its version range | No | Yes |
| The resource files are actually parsed and are valid resource definitions (kind-specific required fields, etc.) | No | Yes |
| Resource IDs are inside the package namespace | No | Yes |
| No duplicate resource IDs across everything loaded | No | Yes |

`verify` examines one package on its own and only confirms that it is unmodified
and compatible, so it succeeds even when a dependency package is missing. A
missing dependency package is first detected by `marmo validate` (or
`load_registry`), which loads the package together with the others and rejects
it before even one resource is registered. A missing lock file, added or deleted
files, hash mismatches, and an incompatible kernel are already rejected at the
`verify` stage. Run both before publishing.

The lock verifies that local content has not changed since review; it is not a
cryptographic signature proving the author's identity. Signatures and public
registries are out of scope for v3. Do not recreate a lock file for untrusted
downloads without first inspecting their contents yourself.

You can record the source relative to a parent directory as follows. Absolute
paths and `..` are rejected.

```bash
marmo package lock ./packages/operations --source packages/operations
```

## Python API

```python
from marmo_core import load_registry, verify_local_package

package = verify_local_package("./my-package")
print(package.manifest.identity)

registry = load_registry(["./my-package"])
```

To check compatibility with a different kernel version in advance, use
`load_registry(..., kernel_version="0.4.0")` or
`verify_local_package(..., kernel_version="0.4.0")`.

## Pre-publication checklist

1. Use a namespace you control, and place every resource ID under it.
2. Update the package and each resource's SemVer as intended.
3. Declare only the permissions, side effects, trust level, and isolation level needed.
4. List the packages and resources that the package depends on.
5. After `marmo package lock`, review the manifest, source, and all hashes.
6. Run `marmo package verify` and `marmo validate`.
7. For executable Tools and Agents, provide an integration test that goes through the Policy Gateway.
